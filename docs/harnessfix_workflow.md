# HarnessFix workflow

This note describes how the HarnessFix agent harness repair method (arXiv 2606.06324) and its repository run. A repository statement cites the file and line at commit 9167a0b of `/data/wang/junh/githubs/method-repos/HarnessFix`, the repository the paper links in §I, footnote 1. A paper statement cites the paper section or table.

## 1. What the method takes as input

- HarnessFix takes raw execution traces and the harness artifacts that shape them (§III-A). The paper names prompt templates, tool specifications, orchestration code, configuration files, adapters, logging hooks and verification scripts as harness artifacts (§II-A).
- Failure attribution takes a failed execution trace together with its external evaluation result (§III-B1).
- For each benchmark the paper selects one initial harness H0 and randomly partitions the sampled tasks into training, validation and held-out test sets (§IV-B).
- The code has one pipeline per benchmark. The entry points are `run_pipeline_swe.py:1045`, `run_pipeline_gaia.py:879`, `run_pipeline_appworld.py:526` and `run_pipeline_terminal_bench.py:569`.
- Each pipeline takes a task model `--model` and an analysis model `--analysis-model` (`run_pipeline_swe.py:1049`, `:1051`). It reads the initial harness from a fixed source directory (`run_pipeline_swe.py:61`, `run_pipeline_gaia.py:51`, `run_pipeline_appworld.py:27`, `run_pipeline_terminal_bench.py:26`) and the train and validation subsets from `data/` (`run_pipeline_swe.py:57` to `:60`, `run_pipeline_gaia.py:52` to `:53`, `run_pipeline_appworld.py:28` to `:29`, `run_pipeline_terminal_bench.py:33` to `:34`).
- The sampling scripts write these subsets. The AppWorld script draws train tasks from the AppWorld `train` split, validation tasks from `dev` and test tasks from `test_normal` and `test_challenge` (`data/sample_appworld.py:72` to `:74`). The Terminal-Bench script reads its split from `data/terminal_bench_splits.json` (`data/sample_terminal_bench.py:19`, `:141`), and that file is not in the repository.
- For each failed train task the analysis agent receives a sanitized copy of the trace, the raw trace path, the evaluator artifacts, the task description, the harness source directory and the HTIR file (`failure_analysis/run_analysis.py:658` to `:669`). For SWE-Bench Verified the evaluator artifacts are the evaluation report and the test output (`run_analysis.py:494` to `:505`). For GAIA the agent also receives the question, the expected answer and the predicted answer (`run_analysis.py:872` to `:875`). For AppWorld it receives the evaluation result and report (`run_analysis.py:1029` to `:1030`). For Terminal-Bench it receives the ATIF trajectory, the verifier stdout and stderr and the terminal pane (`run_analysis.py:1194` to `:1198`).
- For SWE-Bench Verified the analysis prompt also holds `failure_analysis/task_agent_impl_doc.md` when that file exists (`run_analysis.py:478` to `:489`, `:1350`). `failure_analysis/explore_task_agent.py` writes that file (`:2` to `:8`). A search of the four pipeline scripts finds no call to it.

## 2. How it proposes a change

- HarnessFix uses four LLM agents in the paper. They are the trace abstraction agent, the diagnosis agent, the repair agent and the validation agent (§III).
- The trace abstraction agent builds the Harness-aware Trace Intermediate Representation (HTIR). It models each step as a TraceStep with request and response messages and infers a role, an execution status and an artifact/state effect (§III-A1). It derives data-flow links by searching earlier TraceSteps for explicit and semantic reuse (§III-A2) and control-flow links by matching each transition against harness execution logic (§III-A3). It derives implementation anchors that point to a repository path and line range or to a prompt, configuration, tool schema, workflow node or validator identifier (§III-A4). It maps each TraceStep to ETCLOVG layers (§III-A5).
- The diagnosis agent runs symptom localization, evidence backtracking to a ranked set of candidate TraceSteps, candidate adjudication and layer assignment on each failed trace (§III-B1). It writes a diagnosis record with an attribution result, a failure signal and a harness diagnosis (§III-B1).
- The diagnosis agent indexes diagnosis records by implicated layers, treats records with overlapping layers as merge candidates and merges those with the same recurring flaw into flaw records (§III-B2).
- The repair agent retrieves candidate operator groups from Table II by the implicated layers, filters them by root cause and evidence, and designates one primary operator and auxiliary operators (§III-C1). It instantiates a repair specification with target and scope, edit constraints that list allowed and forbidden artifacts, and required behavior (§III-C2). It then generates a candidate patch under that specification (§III, §III-D).
- In the code each iteration first calls the benchmark runner with the current base harness on the train subset and evaluates the output (`run_pipeline_swe.py:1156` to `:1171`). The failed tasks are those listed in `empty_patch_ids`, `unresolved_ids` and `error_ids` of the evaluator output (`run_analysis.py:391` to `:409`).
- HTIR is compiled by Python rules with no model call (`failure_analysis/htir.py:931` to `:948`, `run_analysis.py:631` to `:637`). The TraceStep role is `task_context`, `submission`, `verification`, `agent_action` or `agent_reasoning`, chosen from node types (`htir.py:665` to `:675`). The execution status is `exception`, `submitted`, `verified`, `observed` or `recorded` (`htir.py:710` to `:719`). The external effect is a flag with counts of API calls, mutating calls and database changes (`htir.py:722` to `:747`).
- Data-flow links are substring matches. The probe is an earlier output, lowercased and cut to at most 240 characters, and outputs shorter than 40 characters give no probe. A later model request that contains the probe is linked to it, with at most six earlier sources per request (`htir.py:62` to `:64`, `:86` to `:95`, `:125` to `:177`).
- Control-flow edges are added by fixed rules while the trace is compiled, for example from a parser node to a tool call and from a tool call to a submission (`htir.py:1109`, `:1156`). Layers come from fixed maps of node component and node type to ETCLOVG layer names (`htir.py:408` to `:432`, `:461` to `:472`).
- The anchors in the HTIR file are outcome anchors built from evaluator artifacts (`htir.py:261` to `:269`). A search of `failure_analysis/` finds no field that holds a repository path and line range anchor.
- The analysis agent is a mini-swe-agent `DefaultAgent` with a local shell (`run_analysis.py:644` to `:653`). The SWE-Bench Verified prompt has it read a trajectory summary, the evaluation report and the test output, optionally a compact HTIR view, and the harness source when needed (`failure_analysis/analysis_config_swe.yaml:60` to `:77`, `:147` to `:172`). The GAIA, AppWorld and Terminal-Bench prompts also mark the HTIR view as optional (`analysis_config_gaia.yaml:194`, `analysis_config_appworld.yaml:106`, `analysis_config_terminal_bench.yaml:131`).
- The agent writes a JSON diagnosis with `failure_manifestation`, `failure_reason`, `agent_design_issue`, `affected_component`, `defect_class`, `severity` and `confidence` (`analysis_config_swe.yaml:176` to `:199`). The JSON templates of the four prompts have no field for responsible steps or implicated layers (`analysis_config_swe.yaml:225` to `:239`, `analysis_config_gaia.yaml:257` to `:272`, `analysis_config_appworld.yaml:160` to `:175`, `analysis_config_terminal_bench.yaml:154` to `:167`).
- When the diagnosis has no responsible steps, the code takes the last four steps whose status is `exception`, `submitted` or `verified`, or else the last four steps. It takes the layers of those steps from the HTIR file (`run_analysis.py:273` to `:292`, `:304` to `:332`). Keyword rules fill `defect_class` and `recommended_operator_family` when they are missing or invalid (`run_analysis.py:337` to `:341`, `failure_analysis/operator_registry.py:601` to `:704`).
- Consolidation in the code puts each diagnosis into one bucket per implicated layer, so a diagnosis with several layers enters several buckets (`failure_analysis/consolidation.py:105` to `:119`). Buckets of size one are kept (`failure_analysis/aggregate_results.py:1270`). The docstring leaves semantic clustering to the aggregation model (`consolidation.py:106` to `:111`).
- The aggregate planning agent is a second mini-swe-agent `DefaultAgent` with a local shell (`aggregate_results.py:1037` to `:1099`). It reads context files with the layer buckets, the compact diagnoses, the operator registry, up to eight memory entries, the validation regression analyses and the previous plan and iteration report (`aggregate_results.py:88`, `:946` to `:974`, `:1312` to `:1353`). Its prompt tells it to cluster semantically inside each layer bucket, to inspect source code and not to modify any files (`aggregate_results.py:984` to `:989`).
- The aggregate agent returns a Markdown plan and a JSON spec with `plan_metadata`, `edit_budget` and `fixes` (`aggregate_results.py:268` to `:305`, `:1116` to `:1146`). `edit_budget` holds the allowed paths, the forbidden paths and the maximum number of files. Each fix holds target files, target symbols, a required behavior delta, regression risks and the parts that must not change. When the JSON block fails to parse, one direct model call converts the plan into a spec (`aggregate_results.py:1411` to `:1426`).
- The operator registry holds 18 operator families (`operator_registry.py:37` to `:56`). Each family lists target defect classes and has no harness layer field (`operator_registry.py:7` to `:19`). The enrichment step gives each fix one `operator_family` and fills its target metrics, static checks, rollback conditions, regression risks and allowed paths from the registry (`consolidation.py:299` to `:342`). A search of the code finds no primary or auxiliary operator field.
- The modify agent copies the current base harness into a new candidate directory (`run_pipeline_swe.py:524` to `:531`) and edits files there under the plan and spec (`enhancement_implementation/config_swe.yaml:93` to `:122`). It runs `py_compile` after each edit and a self-check before it submits (`config_swe.yaml:186`, `:190` to `:236`). The modify agent uses the analysis model (`run_pipeline_swe.py:1201`).
- In GAIA, AppWorld and Terminal-Bench the runner is called with the candidate on the train subset. When the train net change is not positive, the candidate is deleted and the modify step runs again with the train comparison file, up to `--max-modify-retries` extra times with default `2` (`run_pipeline_gaia.py:893`, `:459` to `:460`, `:1002` to `:1090`). After the last attempt the candidate goes to the validation gate (`run_pipeline_gaia.py:1088` to `:1090`). The SWE-Bench Verified pipeline calls the runner with the candidate on the train subset and only records the comparison (`run_pipeline_swe.py:650` to `:652`, `:1243` to `:1275`).

## 3. How it decides to keep or reject a change

- In the paper the HarnessFix validation agent first runs pre-validation checks on the candidate diff. They test conformance to the repair specification and basic implementation correctness such as syntax and static analysis (§III-D).
- It then evaluates the candidate on a held-out validation set. It checks that the candidate mitigates the target flaw and avoids unacceptable regressions on tasks previously solved by the original harness. A patch is accepted only if it achieves the target improvement and stays within the regression limit (§III-D). The paper gives no value for the target improvement or the regression limit (§III-D).
- The paper does not state how many runs the acceptance check uses. Its reported task scores are means over three independent runs (§IV-D).
- The outcome is recorded as harness repair memory with the flaw record, the layers, the repair specification, a diff summary, the check results, the regressed validation tasks and a natural language description of when the repair applies (§III-D).
- In the code the pre-validation audit compares the candidate directory with the base. It fails when more files change than `max_files_to_modify`, when a forbidden path is touched, when a changed file is outside the allowed paths, when a fix leaves its target files untouched or when a changed `.py` file fails `compile` (`failure_analysis/plan_diff_audit.py:59` to `:69`, `:72` to `:102`). The audit does not read the `static_checks` field (`plan_diff_audit.py:72` to `:114`). The modify agent receives that field as an instruction (`consolidation.py:322`, `config_swe.yaml:97`).
- SWE-Bench Verified rule. A candidate is promoted only when five checks all pass (`run_pipeline_swe.py:780` to `:787`). The audit passed. The validation net change in resolved tasks against the current base is at least `--min-improvement`, default `1`. At least `--min-target-metrics` target metrics improved, default `1`. The error rate rose by at most `--max-error-rate-delta`, default `0.15`. The invalid submission rate rose by at most `--max-invalid-rate-delta`, default `0.15` (`run_pipeline_swe.py:1061` to `:1068`).
- For SWE-Bench Verified both rates are the share of tasks in `error_ids` (`failure_analysis/validation_metrics.py:100`, `:102`). The rule has no limit on the regression count. Regressed tasks enter only through the net change (`run_pipeline_swe.py:724` to `:727`, `:780` to `:786`). The cost ratio is recorded and `cost_gate_enabled` is `False` (`run_pipeline_swe.py:805` to `:806`).
- GAIA, AppWorld and Terminal-Bench rule. A candidate passes when the net change in resolved validation tasks is at least `--min-improvement`, at least one target metric improved with a mean target delta of at least `--min-target-improvement`, and the regression count is at most `--max-regression` (`failure_analysis/check_val_gate.py:65` to `:79`). The pipelines pass `--min-improvement` with default `1` and `--max-regression` with default `2` (`run_pipeline_gaia.py:895` to `:897`, `run_pipeline_appworld.py:535` to `:536`, `run_pipeline_terminal_bench.py:577` to `:578`). `--min-target-improvement` defaults to `0.0` and the pipelines do not set it (`check_val_gate.py:41`, `run_pipeline_gaia.py:684` to `:697`). The cost ratio is printed as reported only (`check_val_gate.py:99`).
- A regression is a validation task resolved by the current base and not by the candidate (`check_val_gate.py:51`, `run_pipeline_swe.py:726`).
- The target metrics are the `target_metrics` of the spec fixes. A metric improves when the candidate beats the base by more than `1e-9` in the direction of that metric (`validation_metrics.py:359` to `:392`). A metric that the metric function of the benchmark does not compute reads as `0.0` for both runs (`validation_metrics.py:371` to `:372`).
- The registry defines `validation_thresholds` per operator family (`operator_registry.py:132`). Only `thresholds_for_family` reads them (`operator_registry.py:745` to `:747`), and a search of the code finds no caller of that function.
- Runs and tasks. Each candidate gets one call of the benchmark runner on the validation subset, filtered to the validation ids (`run_pipeline_swe.py:583` to `:609`). The comparison base is the stored validation run of the current promoted version. Before the first promotion this is the run of the original harness made at bootstrap (`run_pipeline_swe.py:1128` to `:1141`, `:1297` to `:1308`). The validation subsets are `verified_val_50`, `gaia_val_30`, `appworld_val_45` and `terminal_bench_val` (`run_pipeline_swe.py:58`, `run_pipeline_gaia.py:53`, `run_pipeline_appworld.py:29`, `run_pipeline_terminal_bench.py:34`). The random split option of the Terminal-Bench script defaults to 17 validation tasks (`data/sample_terminal_bench.py:124`).
- A promoted candidate becomes the base of the next iteration (`run_pipeline_swe.py:1337` to `:1342`). The loop runs at most `--max-iterations` iterations, default `3` (`run_pipeline_swe.py:1059`, `run_pipeline_gaia.py:891`). The SWE-Bench Verified loop also stops after `--max-promotion-failures` consecutive rejections, default `2` (`run_pipeline_swe.py:1069`, `:1361` to `:1363`). The README examples pass `--max-iterations 1` (`README.md:99`). At the end the pipeline reports the version with the most resolved validation tasks (`run_pipeline_swe.py:961` to `:969`, `:1365` to `:1369`).
- A candidate that fails the audit is rejected without a validation run (`run_pipeline_swe.py:1213` to `:1241`, `run_pipeline_gaia.py:1092` to `:1102`).
- Memory. A candidate is recorded as accepted only when it is promoted and its audit passed (`run_pipeline_swe.py:942` to `:946`). The entry holds the mode, the version, the outcome, the plan summary, the defect classes, the operator families, the changed files, the audit and gate results, the failure reasons and the improved and regressed task ids (`failure_analysis/harness_memory.py:110` to `:126`). Retrieval scores entries by overlap of mode, components, defect classes and operator families (`harness_memory.py:50` to `:76`).
- The analysis agent diagnoses the validation regressions of each candidate, and the next plan receives them (`run_pipeline_swe.py:1349` to `:1357`, `aggregate_results.py:1321` to `:1330`).

## 4. What it executes

- HarnessFix evaluates each candidate patch on the validation set in the paper (§III-D). The test set is held out (§IV-B).
- The code runs the task agent during repair. In each iteration the runner is called with the current base harness on the train subset (`run_pipeline_swe.py:244` to `:272`). It is called with the candidate on the train subset (`run_pipeline_swe.py:1244` to `:1259`, `run_pipeline_gaia.py:1037` to `:1052`) and on the validation subset (`run_pipeline_swe.py:1278` to `:1294`). It is called once with the original harness on the validation subset at bootstrap (`run_pipeline_swe.py:1128` to `:1141`).
- The pipelines do not run the test split. They print a test command for the best version (`run_pipeline_swe.py:1023` to `:1042`, `:1370` to `:1371`, `run_pipeline_gaia.py:859` to `:877`, `run_pipeline_appworld.py:643`, `run_pipeline_terminal_bench.py:713`).
- Evaluators. SWE-Bench Verified resolution comes from `swebench.harness.run_evaluation` on `princeton-nlp/SWE-Bench_Verified` (`run_pipeline_swe.py:288` to `:297`, `:612` to `:643`). GAIA correctness comes from `question_scorer` against the expected answer (`eval/eval_gaia.py:70`, `task_agent/open_deep_research/src/open_deep_research/scripts/gaia_scorer.py:34`). AppWorld success comes from `appworld.evaluator.evaluate_task` run in a Docker container (`task_agent/appworld_agent/src/appworld_agent/core.py:342` to `:387`, `eval/eval_appworld.py:60`). Terminal-Bench counts a task as resolved when the Harbor verifier reward is at least `1.0` (`eval/eval_terminal_bench.py:37` to `:47`, `:80` to `:93`).
- The analysis, aggregate and modify agents run shell commands on the local machine (`run_analysis.py:193` to `:220`, `aggregate_results.py:1064` to `:1072`, `run_pipeline_swe.py:564`). As its self-check the SWE-Bench Verified modify agent compiles the candidate files and imports `DefaultAgent` from the candidate (`config_swe.yaml:194` to `:218`).
- Python scripts with no model call compute the accept decision (`run_pipeline_swe.py:757` to `:818`, `check_val_gate.py:28` to `:147`, `plan_diff_audit.py:72` to `:114`).

## 7. How the paper scores the method

- HarnessFix is scored by task completion rate, TCR (§IV-B).
- Benchmarks and splits (§IV-B). GAIA with open-deep-research as H0, 150 of 166 questions, split 60/30/60. SWE-Bench Verified with mini-swe-agent, 250 of 500 instances, split 100/50/100. AppWorld with the official simplified ReAct code agent, 225 of 750 tasks, split 90/45/90. Terminal-Bench 2.0 Verified with Harbor Terminus-2, 85 of 89 tasks, split 34/17/34.
- RQ1 compares HarnessFix with H0 under five LLMs (Table III). It compares HarnessFix with human-designed harnesses and with four self-evolution and repair baselines, GEPA, SCOPE, ReCreate and Meta-Harness, under GPT-5 mini (§IV-C, Table IV). Table IV also reports offline repair token consumption in millions, Tokens (M) (§IV-C). Significance uses one-sided paired sign tests over the repeated-run outcomes (§V-A).
- RQ2 scores diagnosis against labels from three annotators on 20 failed test trajectories per benchmark. The labels are the responsible step, the root cause, the implementation anchor, the harness layer and the repair operator (§IV-D, Table V). §V-B reports step, anchor and operator as accuracy and layer as macro-F1.
