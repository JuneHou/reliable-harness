# SelfHeal deployment on AgentDefect and AgentIssue-Bench

This report describes, step by step, how the SelfHeal repair method (arXiv 2604.17699, repository `/data/wang/junh/githubs/SelfHeal` at commit 812e6a3) was deployed on the AgentDefect dataset and on AgentIssue-Bench. It gives every technical setting, every decision with Jun's own words, every place where our run differs from the SelfHeal or AgentIssue-Bench repository and paper, and every mistake we made with the work it caused to be redone. Line references use the form `file#L86`. Every number is registered in `docs/selfheal_deployment_numbers.md`, which `docs/selfheal_deployment_numbers.py` computes from the run folders.

The work serves the RQ of the project, "How much evidence distinguishes repair effects from stochastic variation?" (`Plan_bench.md#L5`). Its first measure reruns the same method on the same defect and counts how often the repairs succeed and how much they differ (`Plan_bench.md#L39`).

## 1. SelfHeal as published

SelfHeal repairs a buggy LLM agent program in two steps (paper §3). The first step turns a study of fix patterns into one natural language rule per pattern (§3.1). The second step runs two ReAct agents in turn (§3.2). A fix agent reads the buggy code and a one line code intent and writes a complete new version of the code. A critic agent reads the buggy code and the test code and accepts or rejects the new version. The loop runs at most three rounds, and "the last code generated by the fix agent is returned as the final output" after a third rejection (§3.2).

SelfHeal never runs the program. The paper says "SelfHeal does not execute code during debugging" (§4.4). The repository holds no code that scores a repair, and the paper does not say how its "Resolved" column was decided (§4.3.1 and `Detailed Result.xlsx`). The paper evaluates SelfHeal on AgentDefect only (§4.3.1) and says it "requires modifications before adoption for fixing bugs in large-scale agentic systems with multiple files" (§4.4).

`docs/selfheal_workflow.md` sections 1 to 5 trace each of these steps to its lines in the repository.

## 2. Setup shared by both datasets

### 2.1 Models

SelfHeal runs every role on three VT ARC models in turn, gpt-oss-120b first, then GLM-5.3, then DeepSeek-V4.1-Flash. Jun said "let's use free arc api supported model for rerun now." and "all 3. gpt-oss-120b first, then GLM-5.3 then deepseek" (`Plan_bench.md#L83`). The rule summaries, the rules and the code intents use the same model as the repair loop. Jun said "if this is part of the repair, should use same model as arc model". Each model runs five reruns of SelfHeal on every case. Jun said "five times" (`Plan_bench.md#L86`).

### 2.2 Relay

SelfHeal reaches the ARC models through `AgentDefect/SelfHeal/code/relay.py`, which runs on this machine and changes no SelfHeal file. SelfHeal's scripts ask for OpenAI model names (`gpt-5.2`, `gpt-5-mini`, `o3-mini`), which ARC does not serve. The relay receives each chat request on 127.0.0.1, replaces the model name with the run's ARC model and asks ARC for a streamed reply. ARC caps replies that are not streamed at 8000 tokens, and the relay sets no length limit, so the reply length is ARC's default maximum. The relay joins the streamed pieces into one ordinary reply for SelfHeal and appends the request and the real reply to the step's relay log. Request headers, which carry the key, are never logged. Jun said "1. ok" after "what is relay", and the rule against length limits reads "you will NEVER NEVER NEVER set token limit".

### 2.3 Web search

SelfHeal's search function sends each query to DuckDuckGo through the `ddgs` package in place of SerpAPI (`AgentDefect/SelfHeal/code/run_agent.diff`). It keeps up to five results with title and snippet and drops results from stackoverflow.com, as the repository does. Jun said "i don't want to get new API. web search should be free" and then "2. yes" (`Plan_bench.md#L107`). This is the only change to `run_agent.py`.

### 2.4 Temperature

SelfHeal's code asks for temperature 0 (`run_agent.py#L239`, `#L245`). Under the client name `gpt-5.2`, langchain-openai v1.1.6 drops any temperature other than 1 (`langchain_openai/chat_models/base.py#L841-L868`). The logged requests carry no temperature field (first request of `AgentDefect/SelfHeal/GLM-5.3/78188862/rerun_2/relay_log_run_agent.jsonl`). So SelfHeal's calls reach ARC with ARC's default temperature, in our runs and in the repository's own GPT-5.2 path.

### 2.5 Python environments

SelfHeal's code runs in `/data/wang/junh/envs/selfheal`, a virtual environment on the standalone `cpython-3.10.19` at `/data/wang/junh/python/cpython-3.10.19`. It holds every pin of SelfHeal's `requirements.txt`, plus langgraph v1.1.6, which `run_agent.py` imports and the requirements omit, and ddgs v9.16.1 for the search. The two rule scripts call `openai.ChatCompletion`, which the pinned openai v2.14.0 lacks, so they run in `/data/wang/junh/envs/selfheal-openai028` with openai v0.28.1. Jun's rule is "no env should depend on another env".

Both environments were first built on the Python of another environment, `envs/causal`. When that environment was deleted they stopped working. Before the AgentIssue-Bench run they were rebuilt on the standalone interpreter. The new `selfheal` holds the same 73 distributions at the same versions as the old one, installed with `--no-deps` from `AgentIssue-Bench/SelfHeal/inputs/env_selfheal_pins.txt`, and a comparison found none missing and none extra. ## 3. AgentDefect

### 3.1 Dataset and inputs

AgentDefect holds 37 case folders in `AgentDefect.zip`, 36 from Stack Overflow and hf-26 from the HuggingFace forum. Each folder holds `run_buggy.py`, `run_fixed.py`, `test.py`, a readme and `requirements.txt`. SelfHeal reads only `run_buggy.py` and `test.py` (`run_agent.py#L86`, `#L103`).

Four inputs SelfHeal needs are missing from the release and were rebuilt and recorded.
- The fix rules need each training post's title and body. `AgentDefect/SelfHeal/inputs/fetch_posts.py` takes them from the public Stack Exchange API. `fix-pattern.csv` is the StackOverflow sheet of `Fix Patterns.xlsx` with 754 rows over 665 posts. The API returned 660 of the 665 posts, and the 5 it did not return are listed in `fetch_record.json`. Jun said "please continue with question1".
- The code intents are a dataset input of paper §4.2 that the release does not ship. `create_intent.py` rebuilds them from each case's title and body on the run's model. The paper's human check of the intents is a dataset construction step and was not repeated. Jun said "we are "EVALUATE" not "DEVELOP DATASET"".
- hf-26 has no `run_buggy.py`. It was rebuilt from the forum post, starting from the archive's `run_fixed.py`, as `inputs/hf-26_run_buggy.py` with its diff in `inputs/hf-26_run_buggy.diff`. Jun said "Rebuild from the forum post".
- The rules file `make_rules.py` writes is named `fix_pattern_rules.csv`, and `run_agent.py` reads `fix_pattern_summaries.csv`. The driver copies the first to the second name.

### 3.2 Fix rules and intents

For each model, `AgentDefect/SelfHeal/code/driver.py rules` runs SelfHeal's preprocessing scripts unchanged in `AgentDefect/SelfHeal/<model>/rules/`, each behind its own relay. `clean_data.py` strips paragraph tags from the training and test descriptions. `extract_summary.py` writes one summary per training post and leaves out the posts that are AgentDefect cases (`extract_summary.py#L57-L59`). That gives 634 summaries per model, with 31 posts left out. `make_rules.py` joins the summaries into one rule per fix pattern, 24 rules per model. `create_intent.py` writes the 37 intents.

### 3.3 Repair loop

`driver.py repair` runs SelfHeal's `run_agent.py` five times on every case for each model, five reruns at once. Each rerun has its own folder `AgentDefect/SelfHeal/<model>/<case>/rerun_<k>/` with the case's files, the model's rules, a one row intent file, a copy of `run_agent.py`, SelfHeal's result file and the relay log. A rerun whose result file exists is not run again, so a stopped run resumes. `run_model.sh` runs the rules and then the repairs for one model, detached from the session.

gpt-oss-120b and GLM-5.3 first ran before the relay streamed, and both were redone in full with the streaming relay, rules, intents and all reruns (fix plan departure 1). Jun said "gpt-oss and GLM, full". Their first runs are kept in `<model>/_not_streamed/`. DeepSeek-V4.1-Flash ran with the streaming relay from the start.

The kept result has 185 reruns per model and 555 in all. gpt-oss-120b marked 138 reruns ACCEPTED and 47 FAILED. GLM-5.3 and DeepSeek-V4.1-Flash marked all 185 ACCEPTED.

## 4. AgentIssue-Bench

### 4.1 What differs from AgentDefect

AgentIssue-Bench holds 50 issues of real agent system repositories, each packaged in a Docker image with the repository at its buggy commit, the authors' reproduction script and an entrypoint script with the modes `apply_patch` and `test_patched` (AgentIssue-Bench paper §4.1, `motivation_experiment/artifacts/agentissue/entrypoints.json`). An issue has no single `run_buggy.py` and no `test.py`. The SelfHeal paper never ran SelfHeal on AgentIssue-Bench. The plan for this run is `/home/grads/junh/.claude/plans/write-delivery-in-plan-bench-md-calm-clock.md`. Jun asked to "make the experiment plan that we can reuse existing self heal code if anything shared".

The AgentIssue-Bench code in `AgentIssue-Bench/SelfHeal/code/` reuses the AgentDefect code without changing it. `driver.py` loads the AgentDefect `driver.py` and uses its rules step, relay start and records with the root set to the AgentIssue-Bench folder. `run_agent.py` and `relay.py` come from the AgentDefect code folder. The test script loads the AgentDefect test script for its FINAL CODE reader, relay start and program environment.

### 4.2 Inputs

`AgentIssue-Bench/SelfHeal/code/inputs.py` builds the inputs with no model call, one Docker image at a time. 36 of the published images are built for amd64. The other 14 are built only for arm64 and were rebuilt for amd64 as `agentissue-bench-amd64:<tag>` from each image's own build steps (`AgentIssue-Bench/images_amd64/`). Jun said "if able to change to x64 change if not tell me why not".
- Repository files. For 34 issues they come from the image's `/app/source_code_buggy`, keeping the files `git ls-files` lists there.
