# ModularRSI workflow

This note describes how the ModularRSI recursive harness self-improvement method (arXiv 2609.14857) and its repository run. Repository statements cite the file and line at commit ed1e545 of `/data/wang/junh/githubs/method-repos/ModularRSI`, the repository the paper links (`https://github.com/IQuestLab/ModularRSI`). A paper statement cites the section, table or appendix. A path that does not start with `scripts/`, `src/`, `generations/`, `README.md` or `.env.example` is under `src/harbor/agents/terminus_2_modular/`.

## 1. What the method takes as input

- The paper evolves Terminus-2 in Harbor, reorganised into five modules (§3.2). Sandbox initialisation, parallel execution and LLM communication stay outside the evolution scope (§3.2).
- The evolution tasks are executable Harbor tasks built from GitHub, Hugging Face, Kaggle and Linux kernel documentation. Each has task specific tests and a reference `solution.sh` that passes them (§4). The paper evolves on 120 instances from each of the TB-related and SWE-related subsets of the 2,000 curated instances (§5.3, §6.1).
- The launcher `scripts/evolve.sh:139` calls `python -m harbor.agents.terminus_2_modular.self_evo.phase0`. The entry point is `main` at `self_evo/phase0.py:171`. It calls `run_online_evo` at `self_evo/online_evo.py:2499`.
- The code takes a dataset folder that holds `tasks/` (`self_evo/phase0.py:71` to `:73`). The default is `../ModularRSI_2000_Instances/tb` (`scripts/evolve.sh:23`). With the `train` split it keeps the `manifest.json` rows marked `train`, or the names in `train_120.txt` (`self_evo/phase0.py:90` to `:100`). Names in `PROBE_CONTAMINATION.json` are removed (`:76` to `:82`).
- The code evolves one module per run, given as `--locked-module` from `agent_loop`, `observation`, `context_mgmt`, `tools` and `verification` (`self_evo/phase0.py:21` to `:27`, `:134`). A reflection without a locked module raises an error (`self_evo/online_evo.py:2088` to `:2089`).
- Generation 0 is a copy of the package `modules/` folder (`self_evo/online_evo.py:2559` to `:2563`).
- The editor reads every module file. It writes only under the locked module folder and never writes `baseline.py` or `active_bundle.json` (`modules/tools/editor_file_tools.py:241` to `:274`). A `tools` run may also write `tool_helper/` (`:271` to `:272`). `protocols.py`, `services.py`, `agent.py`, `library.py` and the `composer/` folder are off limits (`:218` to `:231`).
- The editor may also read the solver output folder with the raw trajectories (`self_evo/run_editor.py:140` to `:143`). The analysis prompt points it to `agent/episode-*/prompt.txt`, `response.txt` and the terminal pane, shows each roll's reward and module trace, and blocks the verifier's tests and expected outputs (`self_evo/trajectory_analysis.py:1255` to `:1260`, `:1328` to `:1334`).

## 2. How it proposes a change

The five modules and their interfaces.

| module in the paper (§3.2) | code type | interface in App. B.1 Listing 1 and in the code |
|---|---|---|
| Agent Loop | `agent_loop` | `AgentLoop.run(initial_prompt, original_instruction, observation, context_mgmt, tools, verification, chat, ctx) -> AgentLoopResult` (`protocols.py:334` to `:348`) |
| Observation Management | `observation` | `Observation.capture(prev, ctx) -> tuple[ObsResult, ObsState]` (`protocols.py:236` to `:245`) |
| Tool Use | `tools` | `ToolSet.parse_llm_response(response) -> LLMResponseParseResult` and `ToolSet.execute(call, ctx) -> ToolResult` (`protocols.py:314` to `:320`). The code protocol also declares `setup`, `teardown`, `format_initial_prompt` and `format_continuation_prompt` (`protocols.py:297` to `:312`) |
| Context Management | `context_mgmt` | `ContextMgmt.maybe_compress(chat, original_instruction, ctx)` and `ContextMgmt.force_summarize(chat, original_instruction, ctx)`, both `-> CompressResult` (`protocols.py:268` to `:285`) |
| Task Completion Detection | `verification` | `VerificationLoop.should_terminate(state, ctx) -> tuple[bool, str]` (`protocols.py:323` to `:331`) |

- The Agent Loop coordinates the other four modules and builds the prompts (§3.2, App. B). The shipped `verification` baseline stops after two consecutive completion signals (`modules/verification/baseline.py:15` to `:35`), as App. B describes.
- The paper runs five independent lineages from the same initial harness, each restricted to one module (§3.1). Within a lineage the Code-Modify Agent, which is the agent under evolution, does the analysis and the modification (§3.1).

Steps in the code.

- Rollouts. The paper collects K trajectories per task and sorts tasks into Positive, Contrastive and Negative (§3.3). The code runs each task `attempts=3` times (`self_evo/phase0.py:145`). Roll `r0` picks the bundle with the LLM composer and the later rolls reuse that frozen bundle through the static composer (`self_evo/k_roll.py:196` to `:238`). Under `composer_scope="locked"` only the locked type is chosen among its variants (`self_evo/phase0.py:244`, `composer/llm_dynamic.py:299` to `:316`).
- Batch. A reflection starts after every `reflect_every=10` completed tasks (`self_evo/phase0.py:40`, `self_evo/online_evo.py:3115` to `:3120`). The paper uses a batch size of ten (§5.3). Reflections run in the background, and a window grows past ten tasks while a reflection is still running (`self_evo/online_evo.py:2764` to `:2771`). A batch in which every trial passed is skipped (`:2080` to `:2087`).
- Grouping. The router puts each task's rolls in a bucket (`self_evo/router.py:194` to `:220`). App. I maps Positive to `all_pass_efficient` and `all_pass_wasteful`, Contrastive to `mixed`, Negative to `fixable_fail`, `stuck_fail` and `unreachable_fail`, and excludes `infra_only` (Table 11). The code no longer produces `unreachable_fail` (`self_evo/router.py:25` to `:28`). A pass is a reward of at least 1.0 and a missing reward is an infrastructure case (`:49` to `:58`).
- Pairing. A `mixed` task pairs its first failing roll with its first passing roll (`self_evo/router.py:302` to `:311`). A `fixable_fail` task pairs its first failing roll with the stored pass of the same task when one exists and is analysed alone otherwise (`:312` to `:322`). The paper's Trajectory Memory stores historical trajectories and rewards per task (§3.3). The code stores the latest passing trial folder per task in `history_pass.json` (`self_evo/online_evo.py:1270` to `:1321`).
- Skipped tasks. `stuck_fail` tasks are not analysed (`self_evo/router.py:323`). An all fail task that never passed goes to `stuck_fail` after three reflections without progress and then waits two epochs (`:45` to `:46`, `:207` to `:220`).
- Efficiency. The paper examines Positive tasks for quality and efficiency (§3.3). The code examines only `all_pass_wasteful` tasks, whose passing rolls have a median above 30 episodes or a repeated command ratio above 0.5 (`self_evo/router.py:41` to `:42`, `:101` to `:109`). It does so only when no correctness finding names the locked module (`self_evo/online_evo.py:1464` to `:1476`). Those findings go to local names and the function returns (`:1475` to `:1477`). The ledger ingest and the evidence pass run before this branch (`:1431`, `:1437`).
- Analysis. One read only editor session per task decides whether a change to the locked module would move that task from fail toward pass (`self_evo/trajectory_analysis.py:1226` to `:1304`, `self_evo/online_evo.py:1371` to `:1426`). It ends with a `<contrast_finding>` JSON block holding `is_culprit`, `divergence`, `would_change_outcome`, `fixable_now` and `suggested_change` (`self_evo/trajectory_analysis.py:1286` to `:1299`), as in App. J.1 Listing 3. With no passing partner the same prompt states that no passing roll is available (`self_evo/trajectory_analysis.py:1337` to `:1341`). App. J calls its Listing 6 a schematic description. Its `<failure_finding>` tag is not found in the repository.
- Routing. Each culprit finding goes to one model call that assigns a lane and an action (`self_evo/evidence_pass.py:212` to `:223`). The `incumbent` lane allows `modify` or `replace` of a named variant. The `novelty` lane allows `add`. The `out_of_scope` lane takes no slot (`self_evo/routing.py:13` to `:27`).
- Clustering. The paper consolidates semantically similar diagnoses that target the same function within each batch (§3.4). The code links a finding to an open proposal when the model answers YES to whether both "describe the SAME intervention", and creates a new proposal otherwise (`self_evo/evidence_pass.py:117` to `:131`, `:278` to `:328`). Proposals persist across windows and unselected ones stay open (`self_evo/proposals.py:1` to `:5`).
- Selection. The paper gives each candidate a vote count equal to its number of distinct supporting tasks, ranks by votes and prioritises the top `K=10` (§3.4). The code picks at most one open proposal per lane and at most two in all (`self_evo/portfolio.py:80` to `:132`, `--max-lanes` default at `self_evo/phase0.py:144`). Within a lane it orders by attempts, then age, then distinct support tasks, then windows, then a hash (`self_evo/portfolio.py:60` to `:70`). A search for `vote` and `top_k` under `src/harbor/agents/terminus_2_modular/` finds nothing.
- Modification. Each selected proposal gets a fresh copy of the current generation's modules (`self_evo/dual_implement.py:342` to `:343`). An editor session receives the direction, the causal hypothesis and every supporting finding (`self_evo/dual_implement.py:110` to `:137`, `:191` to `:243`), as in App. J.2. The two lanes run at the same time (`self_evo/dual_implement.py:372` to `:376`). A session that never emits `<commit_patch/>` counts as failed (`self_evo/run_editor.py:212` to `:222`). A lane that the reviewer rejects as a flawed implementation gets one second build with the reviewer's brief (`self_evo/two_lane.py:113` to `:176`).
- Evolution History. The paper records past code changes per function and the Code-Modify Agent uses them (§3.4). The code writes `editor_memory.jsonl` and `evolution_log.jsonl` (`self_evo/online_evo.py:2392` to `:2413`, `:2449` to `:2459`). No caller of the memory renderer `compact_index` (`self_evo/editor_memory.py:66`) and no reader of `evolution_log.jsonl` is found in `src/`. The editor has a read only `archive` action for niche and genealogy from `archive.json` (`modules/tools/editor_file_tools.py:824` to `:830`).
- Task-Aware Function Composition. The paper gives an LLM the task description and every function description and activates the selected subset, during trajectory collection and downstream evaluation (§3.7). The code's `LLMComposer` makes one call per task that picks one variant for each type with more than one variant and may leave out solver helpers (`composer/llm_dynamic.py:352` to `:442`). It keeps one variant per niche cell (`:231` to `:252`). After a failed call it uses the default bundle (`:202` to `:219`).
- Function Merge. The paper has an LLM merge functions with similar or overlapping behaviour within a module during evolution (§3.7). No such step is found in `self_evo/`. The niche gate rejects a new variant in an occupied niche cell unless it declares `SUPERSEDES` (`self_evo/online_evo.py:890` to `:895`, `:1660` to `:1674`). The archive accepts a `merge` change type from the editor's variant metadata (`archive.py:9`, `:63`).
- Cross-Module Integration. The paper combines the five evolved lineages and runs one more integration epoch with the Code-Modify Agent (§3.6, App. J.4). No integration step is found in the repository and the App. J.4 prompt text is not found. `generations/merged_active` is described as a generation "assembled from previously selected self-evolution variants" (`generations/merged_active/README.md:3` to `:4`). No script that assembles it is found.
- Every step above uses the single `--model` model (`self_evo/phase0.py:135`). Section 5 lists the steps.

## 3. How it decides to keep or reject a change

- The paper's rule. A function update must pass Program Check, Diff Review and Execution Validation in that order. A failure at any gate rolls back using the recorded diffs (§3.5, App. C). Execution Validation samples two tasks from the current batch at random and runs them with the modified harness to detect runtime errors or violations of the execution protocol (§3.5, App. C). App. K.4 reports that "All four sanity rollouts select the new Tools variant".
- The code's rule. `_gate_and_promote` keeps a candidate only when all of the following hold, in this order (`self_evo/online_evo.py:1480` to `:2007`).
  1. The editor committed and made at least one edit (`:1538` to `:1548`).
  2. Smoke passes. Smoke runs AST, import, library load, bundle config, discovery contract and static contract checks (`self_evo/smoke_tests.py:710` to `:720`). App. C lists AST validation, import checks, protocol compliance, discovery contract verification and static self attribute audits. A smoke failure starts up to `MAX_GATE_REPAIRS=2` repair sessions (`self_evo/phase0.py:63`, `self_evo/online_evo.py:1561` to `:1615`).
  3. The action gate finds that the change matches the routed action (`self_evo/online_evo.py:1639` to `:1658`).
  4. The niche gate passes (`:1660` to `:1674`).
  5. The review session submits `accept` (`:1682` to `:1709`). The review prompt hides rewards (`self_evo/trajectory_analysis.py:979` to `:989`), as App. J.3 states. A review that times out or errors passes as `skipped` (`self_evo/online_evo.py:1083` to `:1098`). A review with no structured verdict passes once. Promotion is blocked after three such reviews in a row, or when at least ten reviews exist and more than a tenth were skipped (`:1107` to `:1136`, `self_evo/review_verdict.py:122` to `:126`).
  6. The sanity gate passes (`self_evo/online_evo.py:1761` to `:2002`). It pins the changed variant (`:1763` to `:1827`) and runs the four tasks in `DEFAULT_SANITY_TASKS` once each (`:113` to `:118`, `:1778` to `:1780`). `phase0` passes `sanity_tasks=None`, so these four are used (`self_evo/phase0.py:236`). A run fails the gate only on a code break. A run that returns any reward is not a break, and timeouts and sandbox errors are not breaks (`self_evo/online_evo.py:256` to `:324`). The pinned variant must be selected and must record at least one module trace call (`:593` to `:606`, `:1912` to `:1918`). A crash starts up to two repair sessions, and the four tasks run again after each (`:1929` to `:2002`).
- No reward comparison. The batch's mean reward on the current generation is recorded as a reference and is "never used to gate" (`self_evo/online_evo.py:1745` to `:1752`). The log comment says promotion "now means only 'passed the crash sanity gate'" (`:2474` to `:2476`). The README lists a before and after comparison of the current and modified harness on the same tasks as a future release (`README.md:48` to `:50`).
- Runs used. Per candidate the decision uses one review session and one sanity battery of four task runs, plus one more battery after each repair (`self_evo/online_evo.py:1778` to `:1780`, `:1929` to `:2002`).
- Tasks used. The review reads the batch's trajectories (`self_evo/online_evo.py:1683` to `:1699`). The sanity tasks are TerminalBench 2.0 tasks. `_run_same_bundle_battery` passes no task folder (`self_evo/online_evo.py:219` to `:231`), so `run_harbor_task` runs `-i <task> -d terminal-bench@2.0` (`self_evo/task_runner.py:94` to `:97`). The run log states "probe/sanity/parent held-out on tb2 (terminal-bench@2.0)" (`self_evo/online_evo.py:2579` to `:2585`). After a crash the repair session reads the crashed sanity trial folder (`:1960` to `:1978`). App. A Table 7 marks ModularRSI as excluding benchmark instances, trajectories and benchmark derived rewards from harness evolution.
- Two lanes. When both lanes pass, the `incumbent` lane is promoted first and the `novelty` lane is rebased onto it (`self_evo/promotion.py:31` to `:37`, `:90` to `:127`). The review verdict is reused when the diff is unchanged, while smoke, activation and routing run again (`:45` to `:55`, `:77` to `:87`, `self_evo/two_lane.py:392` to `:443`).
- Rejection. A rejected candidate's staging copy is deleted and no generation is created (`self_evo/online_evo.py:1540`, `:1571`, `self_evo/two_lane.py:327`). A direction whose second build is also rejected becomes `taboo` (`self_evo/proposals.py:55` to `:56`, `self_evo/two_lane.py:317` to `:326`).
- Later retirement by reward. After each reflection the code compares every live variant of the locked module with the `baseline` variant on the tasks where both ran (`self_evo/online_evo.py:2921` to `:2960`). A variant is set to `superseded` when at least three such tasks exist and its pass rate is lower by more than 0.34 (`self_evo/confirm.py:81` to `:102`, `:253` to `:301`). Solver helpers get the same test on rolls with and without the helper (`self_evo/confirm.py:176` to `:224`). The samples are the rolls on the evolution tasks (`self_evo/confirm.py:242` to `:250`, `self_evo/online_evo.py:3051` to `:3066`). The paper describes rollback only after a gate failure (§3.5, App. C).
- `combined_robust`. App. K.4 reports that `tools/combined_robust.py` passed review and sanity checks and was promoted in generation 9. The composer never offers `combined_robust` to the solver, with the comment that it was "quarantined after a held-out TB2 regression" (`composer/llm_dynamic.py:48` to `:61`, `generations/merged_active/README.md:33` to `:36`).

## 4. What it executes

- The paper runs the harness on the evolution tasks and a task specific evaluator gives each trajectory a binary reward (§3.3). Execution Validation runs two tasks with the modified harness (§3.5).
- The code runs the agent during evolution. Each roll is `harbor run -a terminus-2-modular -p <task folder>` with `--ak modules_root=<generation>`, in Docker or E2B (`self_evo/task_runner.py:82` to `:109`, `self_evo/online_evo.py:2805` to `:2853`). Each task runs three times in each of three epochs, and the task order is shuffled per epoch (`self_evo/phase0.py:42`, `:145`, `self_evo/online_evo.py:2601` to `:2611`). The paper evolves each module for three epochs (§5.3).
- Pass or fail comes from Harbor's verifier. It uploads the task's tests into the environment and runs the test script (`src/harbor/verifier/verifier.py:131` to `:185`). The runner reads `verifier_result.rewards.reward` from the trial `result.json` (`self_evo/task_runner.py:197` to `:213`, `self_evo/trajectory_analysis.py:495`). A reward of at least 1.0 is a pass (`self_evo/router.py:49` to `:50`).
- The sanity gate runs the four `DEFAULT_SANITY_TASKS` from TerminalBench 2.0 once each per battery (`self_evo/online_evo.py:113` to `:118`, `:1778` to `:1780`, `self_evo/task_runner.py:96` to `:97`).
- Editor sessions run no container (`self_evo/run_editor.py:194` to `:198`). Their `validate` action runs the smoke checks on the staging copy (`modules/tools/editor_file_tools.py:1226` to `:1236`).
- The routing probe asks the composer which variant it would pick for the batch tasks. It runs no task and is recorded without gating (`self_evo/online_evo.py:1617` to `:1637`).

## 7. How the paper scores the method

- Benchmarks. TerminalBench 2.0 with 89 tasks and SWE-Bench-Verified with 500 tasks, both run under Harbor (§5.1). The No-Evol baseline is Terminus-2 (§5.3).
- Metrics. Accuracy is the mean success over all rollouts. Pass@3 counts a task as solved when at least one of three rollouts succeeds. Pass^3 counts it only when all three succeed. StepNum is the mean number of agent environment steps per rollout (§5.2).
- Results. Cross benchmark transfer is Table 1 (§6.1). Cross model transfer is Table 2 (§6.2) and other evolution models are Table 8 (App. D). Modular evolution against joint and non modular evolution is Table 3, and single module evolution is Table 4 (§6.3). The ablations of CTA, FLM and VG are Table 5 (§6.4). Meta-Harness and AHE are Table 6 (§6.5, App. F). Scaling with evolution data is Fig. 2 (§6.6). Evolution data difficulty is Table 10 and Fig. 5 (App. H).
- Statistics. Each fixed harness is evaluated three times, each task's outcomes are averaged, and 100,000 paired bootstrap resamples over tasks give 95% intervals (App. G, Table 9).
- Evolution curve. Harnesses from successive generations are scored by benchmark reward and by an Opus-4.8 judge that rates five dimensions on a `1` to `5` scale and normalises the mean to `0` to `100` (App. M, Fig. 6, Listing 11).
- Code. `scripts/evaluate.sh` runs `harbor run -d terminal-bench@2.0 -a terminus-2-modular` on `generations/merged_active/gen_0/modules` with the `llm_dynamic` composer (`scripts/evaluate.sh:23` to `:24`, `:33`, `:88` to `:106`). Its defaults are one attempt per task, the task `fix-git` and temperature `0` (`:25`, `:29`, `:31`). Harbor's pass@k routine uses `k` in `{2, 4, 8, ...}` and multiples of `5` (`src/harbor/utils/pass_at_k.py:71` to `:82`). No code for Pass^3, StepNum, the bootstrap or the trajectory judge is found in `src/` or `scripts/`.
- README. The README results table gives 49.40 on TerminalBench 2.0 and 76.45 on SWE-Bench Verified for the SWE-related evolution set (`README.md:76`). Table 1 gives 49.44 and 76.40 for the same cells (§6.1). The README links its table to Table 2 of version 1 of the paper (`README.md:68`). The saved paper HTML is version 2 (front matter, `arXiv:2609.14857v2`).
