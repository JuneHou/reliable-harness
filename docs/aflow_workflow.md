# AFlow workflow

This note describes how the AFlow agentic workflow generation method (arXiv 2410.10762) and its repository run. A repository statement cites the file and line at commit 3f45721 of `/data/wang/junh/githubs/method-repos/AFlow`, whose git remote is `https://github.com/FoundationAgents/AFlow`. A paper statement cites the section, table, figure or appendix of the arXiv HTML version.

## 1. Input

- The search takes an evaluator G, a dataset D and an operator set O (§4, Algorithm 1). It starts from a template workflow W0 that the optimizer completes by filling in its call function (§4 Initialization, App. A.3). The paper calls this start a blank template that contains only a single node without prompts (§5.2 Case Study).
- In the code the start workflow is `workspace/<dataset>/workflows/round_1/graph.py`. For GSM8K, MATH, HotpotQA and DROP it calls `Custom` once with an empty instruction (`workspace/GSM8K/workflows/round_1/graph.py:24`). For HumanEval and MBPP it calls `CustomCodeGenerate` once with an empty instruction (`workspace/HumanEval/workflows/round_1/graph.py:29`). The matching `prompt.py` holds only a commented example (`workspace/GSM8K/workflows/round_1/prompt.py:1` to `:5`).
- Operators in the paper. Seven operators are named. They are Generate, Format, Review and Revise, Ensemble, Test, Programmer and Custom (§3.2). App. A.4 prints code for ContextualGenerate, CodeGenerate, Format, Review, Revise, Ensemble, Test and Programmer. An operator set per benchmark is not found in §3.2, §5.1 or App. A.4.
- Operators in the code. `run.py` fixes one list per dataset (`run.py:20` to `:56`). HotpotQA and DROP get `Custom`, `AnswerGenerate` and `ScEnsemble`. GSM8K and MATH get `Custom`, `ScEnsemble` and `Programmer`. HumanEval, MBPP and LiveCodeBench get `Custom`, `CustomCodeGenerate`, `ScEnsemble` and `Test`. A workflow imports its operators from `workspace/<dataset>/workflows/template/operator.py` (`scripts/prompts/optimize_prompt.py:52`). `Format`, `Review`, `Revise` and `MdEnsemble` are defined in `scripts/operators.py:340`, `:350`, `:360` and `:370` and appear in no list in `run.py`.
- Dataset split in the paper. D is split at random into a validation set (20%) and a test set (80%) with the seed fixed at 42 (§4 Initialization). §5.1 states the same split as a validation to test ratio of 1 to 4 (§5.1 Datasets). The blank template runs five times on the validation set, and the problems with high score variance become the final validation set (§4 Initialization). App. A.6 writes these steps as lines 4 to 6.
- Dataset split in the code. The search reads `data/datasets/<name>_validate.jsonl` and the test mode reads `data/datasets/<name>_test.jsonl`, with the dataset name in lower case (`scripts/evaluator.py:63` to `:65`). Both files come from an archive that `run.py:120` downloads (`data/download_data.py:68` to `:73`). `va_list = None` keeps every validation problem (`scripts/evaluator.py:50` to `:54`). A split function seeded with 42 is defined (`benchmarks/utils.py:17` to `:42`), and no call to it is found in the repository. A step that selects high variance problems is not found.
- Datasets. `run.py` offers HumanEval, MBPP, GSM8K, MATH, HotpotQA, DROP and LiveCodeBench (`run.py:20` to `:56`). The paper evaluates the first six (§5.1 Datasets).
- Entry point. `python run.py --dataset MATH` (`README.md:78`) runs the main block at `run.py:100`. It builds `Optimizer` and calls `optimizer.optimize("Graph")` (`run.py:122` to `:137`).

## 2. Proposing a change

- Each round runs soft mixed probability selection, LLM-based expansion, execution evaluation and experience backpropagation (§4, Fig. 3). Each tree node is a complete workflow (§4).
- Selection in the paper. The candidates are the top k workflows and the initial workflow (§4 Selection). The probability is `P_mixed(i) = λ·(1/n) + (1−λ)·exp(α(s_i − s_max)) / Σ_j exp(α(s_j − s_max))` (§4 Eq. 3). §4 gives α = 0.4 and λ = 0.2. App. A.6 sets `k = 3`, `λ = 0.4` and `α = 0.2` (lines 3 and 38).
- Selection in the code. `get_top_rounds` takes the `--sample` rounds with the highest mean score, default `4` (`run.py:68`, `scripts/optimizer_utils/data_utils.py:40` to `:59`). Round 1 enters this list only when its score ranks among them, and it is then moved to the front (`data_utils.py:53` to `:55`). `select_round` multiplies each score by 100 and applies the same mixed formula with α = 0.2 and λ = 0.3 (`data_utils.py:16` to `:17`, `:61` to `:109`). It draws one round with `np.random.choice` (`data_utils.py:73`).
- What expansion reads. For the selected round it reads `graph.py` from `class Workflow:` onward and `prompt.py` (`scripts/optimizer_utils/graph_utils.py:38` to `:57`). It also reads the round's mean score, its experience (`scripts/optimizer_utils/experience_utils.py:55` to `:67`), the operator descriptions in `operator.json` (`graph_utils.py:59` to `:73`) and up to three random entries of the round's `log.json` (`data_utils.py:18`, `:111` to `:145`). The call site is `scripts/optimizer.py:135` to `:149`.
- `log.json` holds the problems a workflow got wrong. That is a score of 0 for GSM8K, MATH, HumanEval and MBPP and an F1 below 0.3 for HotpotQA and DROP (`benchmarks/benchmark.py:48` to `:73`, `benchmarks/gsm8k.py:47`, `benchmarks/math.py:121`, `benchmarks/humaneval.py:133`, `benchmarks/mbpp.py:109`, `benchmarks/hotpotqa.py:59` to `:62`, `benchmarks/drop.py:73`). The paper says the experience holds all modifications of the selected workflow with their improvements or failures, along with logs of predictions and expected output (§4 Expansion).
- Experience text in the code. Failed modifications of the parent are listed with their score. Successful ones are listed without a score. Both lines start with `-Absolutely prohibit` (`experience_utils.py:61`, `:63`).
- The optimizer prompt is `WORKFLOW_INPUT` followed by `WORKFLOW_CUSTOM_USE` and `WORKFLOW_OPTIMIZE_PROMPT` (`graph_utils.py:85` to `:95`). App. A.1 prints the text of `WORKFLOW_OPTIMIZE_PROMPT` (`scripts/prompts/optimize_prompt.py:1` to `:13`). App. C.2 quotes the log sentence of `WORKFLOW_INPUT` (`optimize_prompt.py:26`). `WORKFLOW_INPUT` asks for `**Only one detail point can be modified at a time**, and no more than 5 lines of code may be changed per modification` (`optimize_prompt.py:29`). The paper says each iteration employs a single step modification (§5.2 Case Study).
- What expansion edits. The optimizer model returns three XML fields named `modification`, `graph` and `prompt` (`scripts/optimizer.py:26` to `:29`, `:154` to `:160`, `scripts/formatter.py:85` to `:113`). When the format check fails, a plain call and a regex extraction follow (`optimizer.py:164` to `:174`). The new round directory gets `graph.py`, built from `WORKFLOW_TEMPLATE` around the returned `Workflow` class, and `prompt.py` with the returned prompts (`graph_utils.py:115` to `:125`, `optimize_prompt.py:51` to `:60`). The prompt allows new prompts only in `prompt_custom` for `Custom` and prohibits generating prompts of other operators (`optimize_prompt.py:11`). The paper fixes the model, temperature and output format and searches over code edges and prompts (§3.2 Formulation).
- A proposal whose `modification` text equals an earlier modification from the same parent is dropped and the optimizer is called again (`optimizer.py:176` to `:183`, `experience_utils.py:69` to `:80`).
- Model. The optimizer model performs the expansion (`optimizer.py:48`, `:157`). The paper uses Claude-3.5-sonnet as the optimizer (§5.1 Implementation Details).

## 3. Keeping or rejecting a change

- Paper. Each generated workflow runs five times on the validation set, and the mean and standard deviation are computed (§4 Evaluation, App. A.6 lines 15 to 19). The record keeps the workflow's performance, the optimizer's modification of its parent and the success relative to the parent. This experience is propagated back to the parent, and the score is added to the global record for selection (§4 Backpropagation). W* is replaced when the mean score beats the best score so far (App. A.6 lines 22 to 25).
- Code. Every generated workflow is evaluated `validation_rounds` times. Each run appends one row to `workflows/results.json`, and the mean is returned (`scripts/optimizer_utils/evaluation_utils.py:30` to `:53`). `run.py` sets `--validation_rounds` to `1` by default and passes it on (`run.py:78`, `:133`). The default in the `Optimizer` signature is `5` (`scripts/optimizer.py:45`). `README.md:61` lists `--validation_rounds 5`.
- The child's `experience.json` stores the parent round, the modification, the parent score, the child score and `succeed`. `succeed` is true when the child mean is above the parent mean (`experience_utils.py:82` to `:93`). `load_experience` rebuilds the tree of modifications per parent from these files (`experience_utils.py:12` to `:53`).
- An accept or reject step is not found in the code. Every generated round keeps its directory and its rows in `results.json`, and it enters later selection through its rank by mean score (`data_utils.py:171` to `:197`). A best workflow variable like W* is not found in `Optimizer.optimize` (`optimizer.py:71` to `:118`).
- Round 1 is evaluated the same way before the first expansion (`optimizer.py:125` to `:129`).
- A round that raises an exception is attempted once (`max_retries = 1`). Its score is set to `None` and the round counter still advances (`optimizer.py:84` to `:105`).
- Stopping in the paper. The search ends after N rounds, or earlier when the top k average score shows no improvement for n consecutive rounds (§4 Terminal Condition). App. A.6 sets N to 20, k to 3 and n to 5 (line 3) and states the rule as the top k workflows remaining unchanged in n rounds (line 26). §5.1 sets 20 iteration rounds.
- Stopping in the code. The loop runs `--max_rounds` iterations, default 20 (`run.py:76`, `optimizer.py:80`). After each round `check_convergence(top_k=3)` runs (`optimizer.py:108`) with `z=0` and `consecutive_rounds=5` (`scripts/optimizer_utils/convergence_utils.py:68`). For each prefix of rounds it takes the mean of the top three round means. It counts consecutive rounds where the change of this mean is at most `z` times its standard error, and it reports convergence at five (`convergence_utils.py:81` to `:105`). With `z=0` the condition holds only when the mean does not change. At least four rounds are needed (`convergence_utils.py:76` to `:77`). The loop stops on convergence when `--check_convergence` is true, which is its default (`run.py:77`, `optimizer.py:110` to `:116`).

## 4. What is executed

- Paper. AFlow executes the workflows directly to get feedback, because reasoning tasks have explicit evaluation functions (§4 Evaluation). The Executor runs the workflow on the dataset and returns score and cost (App. A.6 lines 49 to 51).
- Code. The search imports each round's `graph.py` as a module (`graph_utils.py:26` to `:36`). It runs the `Workflow` on every validation problem with the executor model, 50 problems at a time (`scripts/evaluator.py:38` to `:61`, `benchmarks/benchmark.py:87` to `:104`). The round score of one run is the mean of the problem scores (`benchmark.py:36` to `:46`).
- The scorers are rules in `benchmarks/` and make no model call.
  - GSM8K. The last number in the output must equal the last number in the answer within `1e-6` (`benchmarks/gsm8k.py:18` to `:32`, `:40`).
  - MATH. The last `\boxed{}` content, or the last sentence when there is none, must equal the reference as a string, as a number within `1e-3`, or symbolically (`benchmarks/math.py:20` to `:57`).
  - HumanEval and MBPP. The solution and the dataset test run through `exec` with a 15 second limit, and the score is 1.0 when the test passes (`benchmarks/humaneval.py:77` to `:86`, `:130`, `benchmarks/mbpp.py:60` to `:69`, `:106`).
  - HotpotQA. Token F1 after normalization (`benchmarks/hotpotqa.py:16` to `:42`).
  - DROP. The maximum token F1 over the answer parts and output parts split at `|` (`benchmarks/drop.py:55` to `:71`).
- Operators also execute code inside a workflow run. `Programmer` runs the generated `solve()` in a separate process with a 30 second limit, blocks a list of imports and tries up to three times (`workspace/GSM8K/workflows/template/operator.py:28` to `:56`, `:63` to `:78`, `:102`). App. A.4 prints `timeout=180` and a thread pool for `Programmer.exec_code`. The code uses `timeout=30` and a process pool (`workspace/GSM8K/workflows/template/operator.py:63`, `:68`, `scripts/operators.py:199`).
- `Test` runs the public tests of the problem through `exec`. On failure it asks the model to reflect and rewrite the solution, for up to three loops (`workspace/MBPP/workflows/template/operator.py:75` to `:144`). The public tests come from `data/datasets/humaneval_public_test.jsonl` and `data/datasets/mbpp_public_test.jsonl` (`scripts/utils/code.py:17` to `:21`). The paper says Test uses the public tests of the dataset, and for MBPP the first test case of each problem (App. A.4).
- Test mode. `optimizer.optimize("Test")` is commented out (`run.py:140`). When called, it evaluates the rounds listed in `rounds = [1]` once on the test file (`optimizer.py:71` to `:78`, `:238` to `:256`).
- App. F scores open ended tasks with GPT-4o as an LLM judge (App. F.1). An LLM judge is not found in the code.

## 7. How the paper scores the method

- Benchmarks. HumanEval, MBPP, MATH, GSM8K, HotpotQA and DROP (§5.1 Datasets). GSM8K, HumanEval and MBPP are used in full. HotpotQA and DROP use 1,000 random samples each. MATH uses 617 problems at level 5 from 4 problem types (§5.1 Datasets).
- Metrics. Solve rate for GSM8K and MATH, pass@1 for HumanEval and MBPP, and F1 for HotpotQA and DROP (§5.1 Metrics, Fig. 1). Cost is tracked from token usage to build a Pareto front of performance against cost (§5.1 Metrics, Fig. 4, App. D).
- Table 1 compares the found workflows with IO, CoT, CoT SC, MedPrompt, MultiPersona, Self Refine and ADAS. All methods run with GPT-4o-mini on the test split three times, and the average is reported (Table 1).
- Table 2 runs the workflows found with GPT-4o-mini and with DeepSeek-V2.5 on four executor models on the HumanEval test split. Each is tested three times and the average is reported (Table 2, §5.2).
- Fig. 5 compares search with and without operators on GSM8K on the validation and test sets (§5.2 Ablation Study, App. B).
- App. F scores two open ended case studies with GPT-4o as an LLM judge and with three human annotators (App. F.1, App. F.2, Table A1, Table A2).
- The code's test mode runs each chosen round once (`test_n = 1`, `scripts/optimizer.py:73`).
