# ACE workflow

This note describes how the ACE (Agentic Context Engineering) method (arXiv 2510.04618) and its repository run. Code pointers refer to commit 82709de of `/data/wang/junh/githubs/method-repos/ACE`, the repository linked in the paper (Reproducibility Statement). Paper pointers cite the section, table or appendix of the v3 HTML version.

## 1. What the method takes as input

- ACE takes a context represented as a playbook of itemized bullets (§3.1). Each bullet holds metadata and content. The metadata is a unique identifier and counters of how often the bullet was marked helpful or harmful. The content is a small unit such as a reusable strategy, a domain concept or a common failure mode (§3.1).
- In the code a bullet is one line `[id] helpful=X harmful=Y :: content` (`playbook_utils.py:15` to `:16`, `:46` to `:48`). Without `--initial_playbook_path` a run starts from an empty playbook with seven section headers (`eval/finance/run.py:23`, `:202`, `ace/ace.py:86` to `:109`).
- Tasks. Offline adaptation optimizes on the training split. Online adaptation goes through the test split in order (§4.1). The benchmarks are AppWorld, FiNER, Formula, DDXPlus and BIRD-SQL (§4.1).
- The code entry point for the finance tasks is `main` in `eval/finance/run.py:179`. It reads the data paths from `eval/finance/data/sample_config.json` (`eval/finance/run.py:192`). It builds `ACE`, or `ACEBatch` when `--batch_size` is above one (`:209` to `:219`), and calls `run` (`:247`), defined at `ace/ace.py:166`.
- The shipped data are FiNER and Formula train, validation and test files (`eval/finance/data/sample_config.json:2` to `:11`). Each sample becomes a question, a context and a target (`eval/finance/data_processor.py:111` to `:120`).
- Ground truth or execution feedback. The "GT labels" column marks whether ground-truth labels are available to the Reflector during adaptation (Table 1, Table 2). Without labels on AppWorld, ACE uses signals available during execution such as code execution success or failure (§4.3). For the finance benchmarks the paper says that "when ground-truth supervision or reliable execution signals are absent, both ACE and DC may degrade in performance" (§4.4).
- In the code the target is always read (`ace/ace.py:461`). By default the Reflector prompt includes the ground truth (`ace/core/reflector.py:65` to `:73`). With `--no_ground_truth` the Reflector and the Curator use prompts without it (`ace/core/reflector.py:74` to `:81`, `ace/core/curator.py:88` to `:97`). In both settings the Reflector receives the feedback string "Predicted answer does not match ground truth" or "Predicted answer matches ground truth", set by comparing the answer with the target (`ace/ace.py:476` to `:477`, `:515`, `:558`).

## 2. How it proposes a change

- ACE divides each update across three roles. The Generator produces reasoning trajectories for new queries. The Reflector distills insights from successes and errors and may refine them over several iterations. The Curator turns the insights into compact delta entries that are merged into the context "by lightweight, non-LLM logic" (§3).
- The paper uses one LLM for all three roles, the non-thinking mode of DeepSeek-V3.1 (§4.2).
- Generator. The paper says the Generator highlights which bullets were useful or misleading (§3.1). In the code the Generator reads the playbook, a reflection, the question and the context (`ace/core/generator.py:59`). It returns JSON with `reasoning`, `bullet_ids` of the bullets it found relevant and helpful, and `final_answer` (`ace/prompts/generator.py:16` to `:19`). The IDs are read from the reply (`ace/core/generator.py:73` to `:117`).
- Reflector. In the code it reads the question, the Generator's reasoning trace, the predicted answer, the ground truth unless `--no_ground_truth` is set, the feedback string and the bullets the Generator cited (`ace/ace.py:505` to `:521`, `ace/core/reflector.py:65` to `:81`). It returns `error_identification`, `root_cause_analysis`, `correct_approach`, `key_insight` and a `bullet_tags` list that tags each cited bullet helpful, harmful or neutral (`ace/prompts/reflector.py:16` to `:24`).
- Reflection rounds. When the first answer is wrong the code runs up to `max_num_rounds` rounds. Each round calls the Reflector, updates the counters and calls the Generator again with the reflection. The loop stops when the new answer is correct (`ace/ace.py:499` to `:545`). When the first answer is correct the Reflector runs once (`ace/ace.py:547` to `:576`). The paper sets the maximum number of Reflector refinement rounds to five (§4.2). The code default is three (`eval/finance/run.py:47`).
- Curator. In the code it runs every `curator_frequency` steps, which is every step by default (`ace/ace.py:579`, `eval/finance/run.py:49`). It reads the playbook statistics, the last reflection, the current playbook, the question context, the current step, the number of samples and the token budget (`ace/core/curator.py:78` to `:97`, `ace/ace.py:584` to `:597`). The prompt asks only for new insights missing from the playbook and says not to regenerate the playbook (`ace/prompts/curator.py:16` to `:18`). The only operation it offers is ADD with a section and content (`ace/prompts/curator.py:49` to `:52`).
- Delta update. The paper's delta context is a small set of candidate bullets distilled by the Reflector and integrated by the Curator (§3.1). In the code `apply_curator_operations` appends each ADD as a new bullet with a fresh ID and both counters at zero (`playbook_utils.py:143` to `:161`). A section name not in the playbook goes to OTHERS (`playbook_utils.py:148` to `:151`). UPDATE, MERGE, DELETE and CREATE_META are listed as not implemented (`playbook_utils.py:100` to `:104`). This merge makes no model call (`playbook_utils.py:96` to `:216`). If the Curator reply is empty or is not valid JSON, the playbook stays as it was (`ace/core/curator.py:113` to `:117`, `:149` to `:167`).
- Counters. The paper updates existing bullets in place, for example by incrementing counters (§3.2). In the code each `helpful` or `harmful` tag from the Reflector adds one to that counter of the tagged bullet (`playbook_utils.py:50` to `:93`, `ace/ace.py:524` to `:527`).
- Grow-and-refine. The paper appends bullets with new identifiers and then runs a de-duplication step that compares bullets via semantic embeddings. Refinement runs after each delta or only when the context window is exceeded (§3.2). The paper tests pruning triggers of 10K, 50K and 100K tokens on FiNER (App. A.6, Table 21).
- In the code the BulletpointAnalyzer runs after each Curator call when `--use_bulletpoint_analyzer` is set (`ace/ace.py:599` to `:606`). It is off by default (`eval/finance/run.py:85` to `:86`). A refinement or pruning trigger based on context length is not found in the code. The `playbook_token_budget`, `80000` by default, appears only as text in the Curator prompt (`eval/finance/run.py:73`, `ace/prompts/curator.py:26`).
- Post-curator generation. After the Curator the code has the Generator answer the same sample again with the updated playbook and records whether that answer is correct (`ace/ace.py:608` to `:628`).
- Multi-epoch adaptation. ACE can revisit the same queries over several epochs (§3). The paper sets the maximum number of epochs in offline adaptation to five (§4.2). The code default is one epoch (`eval/finance/run.py:45`).
- Batch size. The paper adopts a batch size of one, one delta context per sample (§4.2). It also says itemized deltas can be merged in parallel for batched adaptation (§3). The code default batch size is one (`eval/finance/run.py:57`).
- With a larger `--batch_size` the code uses `ACEBatch` (`eval/finance/run.py:209`). It runs the Generator and the Reflector for each sample of the batch in parallel on one playbook snapshot (`ace/ace_batch.py:654` to `:723`). It applies all counter updates once (`:769` to `:772`). It repeats each reflection two times by default and shuffles them (`:133` to `:138`, `:752` to `:760`). It splits them into `max(1, int(original_reflection_count ** 0.5))` groups by default (`:834` to `:839`). Each group's Curator call proposes ADD operations (`ace/core/curator.py:169` to `:251`). An LLM reducer call merges the proposals into one ADD list (`ace/core/curator.py:253` to `:289`, `ace/ace_batch.py:898` to `:908`). `apply_curator_operations` then applies that list (`ace/ace_batch.py:910` to `:915`).

## 3. How it decides to keep or reject a change

- ACE as the paper describes it merges each delta into the context. A test of a delta before it is merged is not found in §3, §3.1 or §3.2. The paper states that ACE avoids GEPA's prompt-validation loop (§4.7) and avoids expensive validation-time re-evaluation (App. A.3).
- In the code each validated ADD operation is applied at once (`ace/core/curator.py:119` to `:147`). The post-curator answer is recorded as `post_train_result` (`ace/ace.py:622` to `:628`). A revert of the playbook based on that answer is not found (`ace/ace.py:608` to `:630`).
- Offline mode in the code has a validation step. Every `eval_steps` steps, 100 by default, the current playbook answers the whole validation set (`ace/ace.py:736` to `:756`, `eval/finance/run.py:51`). The playbook with the highest validation accuracy so far is stored as `best_playbook` (`ace/ace.py:778` to `:784`). The final test uses `best_playbook` (`ace/ace.py:282` to `:294`). Training continues from the current playbook (`ace/ace.py:465` to `:468`). Offline mode refuses to start without validation samples (`ace/ace.py:193` to `:194`).
- A validation step is not found in online mode (`ace/ace.py:877` to `:1142`).
- De-duplication. The paper compares bullets via semantic embeddings (§3.2). It tests de-duplication thresholds of 50%, 70% and 90% on FiNER (App. A.6, Table 20). It says the bullet-point analyzer merges and deduplicates semantically similar bullets and can filter entries flagged as potentially harmful via metadata (App. A.4). It credits the lower cost of ACE to "non-LLM-based context merging and de-duplication" (§4.7).
- In the code the BulletpointAnalyzer embeds the content of each bullet and takes cosine similarity as the dot product of L2 normalized vectors (`ace/core/bulletpoint_analyzer.py:142` to `:146`, `:167`). A later bullet joins the group of an earlier bullet when the similarity is at least the threshold, 0.90 by default (`ace/core/bulletpoint_analyzer.py:172` to `:189`, `eval/finance/run.py:87`). Each group is merged into one bullet by an LLM call whose prompt says to keep the first ID and the summed counters (`ace/core/bulletpoint_analyzer.py:207` to `:241`). If the merged line does not parse, the first bullet of the group is kept (`ace/core/bulletpoint_analyzer.py:265` to `:271`).
- Counters in the code change through Reflector tags and through merges (`playbook_utils.py:79` to `:82`, `ace/core/bulletpoint_analyzer.py:213` to `:214`). The Generator sees them in the playbook text. The Reflector sees them on the cited bullets (`playbook_utils.py:369`). The Curator sees them in the playbook and in the statistics (`playbook_utils.py:218` to `:254`, `ace/ace.py:582`). Removal or filtering of a bullet based on its counters is not found in the code.
- Task runs in the code. For each training sample the code makes one Generator call. It then makes up to `max_num_rounds` pairs of Reflector and Generator calls when the answer is wrong, or one Reflector call when it is right. It makes one Curator call at the default `curator_frequency` and one post-curator Generator call (`ace/ace.py:463` to `:628`). Offline validation adds one Generator call per validation sample every `eval_steps` steps (`ace/ace.py:736` to `:756`).
- Task runs in the paper. On AppWorld offline adaptation ACE used 357 rollouts and GEPA used 1434 (§4.7, Table 4). In the fine-grained cost analysis ACE ran with one epoch and one Reflector refinement round (App. A.3). That run used 2,075 rollouts over 90 queries, of which 1,790 were Generator rollouts (Table 12).

## 4. What it executes

- ACE on AppWorld runs an agent in an execution environment with common applications and APIs (§4.1). All methods build on the official ReAct implementation released by the benchmark authors (§4.2). Without labels, signals such as code execution success or failure guide the Reflector and the Curator (§4.3).
- The AppWorld runner in the repository is the git submodule `ace-appworld` (`.gitmodules:1` to `:3`), pinned at commit 9f3e921 (`git ls-tree HEAD`). Its directory is empty in this checkout. The AppWorld loop is therefore not found in the code read here.
- Offline adaptation optimizes on the training split and is scored on the test split. Online adaptation goes through the test split in order. For each sample the model first predicts with the current context and then updates the context from that sample (§4.1).
- The code has three modes, `offline`, `online` and `eval_only` (`ace/ace.py:190` to `:191`). Offline mode tests the starting playbook on the test set when one is given, trains on the training set and tests `best_playbook` (`ace/ace.py:246` to `:296`). Online mode first tests the starting playbook on the whole test set (`ace/ace.py:300` to `:314`). It then cuts the test set into windows of `online_eval_frequency` samples, 15 by default (`eval/finance/run.py:53`). Each window is first answered with the current playbook and scored, and then each of its samples is used for training (`ace/ace.py:939` to `:1029`). Online mode requires one epoch (`ace/ace.py:907` to `:908`).
- Each finance task attempt in the code is one Generator call. The reply is parsed by `extract_answer` (`utils.py:100` to `:156`) and compared with the target by the task's `answer_is_correct` (`eval/finance/data_processor.py:165` to `:181`). A `subprocess`, `os.system` or `exec` call is not found in the checked out Python files. The FiNER checker calls Python `eval` on each label of the target and of the prediction inside a `try` block (`eval/finance/data_processor.py:142` to `:146`).
- Evaluators. FiNER counts a sample correct when every comma separated label matches (`eval/finance/data_processor.py:126` to `:152`). Formula compares answer and target as floats after removing commas (`eval/finance/data_processor.py:154` to `:162`). The repository also has Mind2Web runners whose checker compares the element index, the operation and the value of an action (`eval/mind2web/data_processor.py:147` to `:186`, `eval/mind2web2/data_processor.py:149`). Mind2Web is not found in the paper.

- The BulletpointAnalyzer calls `chat.completions.create` directly at temperature 0.3 (`ace/core/bulletpoint_analyzer.py:236` to `:241`).

## 6. Embedding model

- ACE de-duplicates bullets by "comparing bullets via semantic embeddings" (§3.2). An embedding model name is not found in the paper.
- The code uses the sentence-transformers model `all-mpnet-base-v2`. It is the default of `BulletpointAnalyzer` (`ace/core/bulletpoint_analyzer.py:76`), and `ACE` passes no other name (`ace/ace.py:70` to `:74`). It is loaded with `SentenceTransformer` (`ace/core/bulletpoint_analyzer.py:100`). The vectors are normalized with `faiss.normalize_L2` (`ace/core/bulletpoint_analyzer.py:146`). The dependencies are `faiss-cpu` and `sentence-transformers` (`pyproject.toml:8`, `:14`).
- If either import fails, the analyzer returns the playbook unchanged (`ace/core/bulletpoint_analyzer.py:13` to `:19`, `:290` to `:292`). The embedding step runs only with `--use_bulletpoint_analyzer` (`eval/finance/run.py:85` to `:86`, `ace/ace.py:599`).

## 7. How the paper scores the method

- ACE on AppWorld is scored by Task Goal Completion (TGC) and Scenario Goal Completion (SGC) on the test-normal and test-challenge splits under the official protocol (§4.1). Results are in Table 1. Ablations are in Table 3 and Table 18. Other LLMs are in Table 5 and Table 6. Reflection rounds are in Table 19.
- FiNER, Formula and DDXPlus are scored by accuracy, the proportion of predicted answers that exactly match the ground truth (§4.1). FiNER and Formula results are in Table 2, with other LLMs in Tables 7 to 9. DDXPlus results are in Table 10 (App. A.2).
- BIRD-SQL is scored by GPT-4o-mini as an LLM judge (§4.1). Results for the Simple, Moderate and Challenging subsets are in Table 11 (App. A.2).
- Offline results are pass@1 accuracy on the test split. Online results come from sequential evaluation on the test split. All methods use the same shuffled test split (§4.1).
- The baselines are the base LLM or ReAct, ICL, MIPROv2, GEPA and Dynamic Cheatsheet in cumulative mode (§4.2).
- Cost is scored by adaptation latency and number of rollouts against GEPA on AppWorld offline, and by adaptation latency and token dollar cost against Dynamic Cheatsheet on FiNER online (§4.7, Table 4). Token counts per role are in Tables 12 to 15 (App. A.3).
- Robustness to reflection quality is scored on FiNER with weaker Reflector models and with harmful reflector feedback (App. A.4, Tables 16 and 17). The de-duplication threshold and the pruning trigger are scored on FiNER (App. A.6, Tables 20 and 21).
- In the code, test accuracy comes from the task's `evaluate_accuracy` (`utils.py:272` to `:273`). For FiNER it is the number of matching labels over the number of labels (`eval/finance/data_processor.py:183` to `:200`). Every FiNER target in the shipped files holds four labels (`eval/finance/data/finer_*.jsonl`, field `target`). For Formula it is the number of correct samples over the number of samples (`eval/finance/data_processor.py:202` to `:220`). Online accuracy is the average of the window accuracies weighted by window size (`ace/ace.py:967` to `:972`, `:1094`).
